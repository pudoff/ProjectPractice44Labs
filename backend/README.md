# Backend

Монолит: один API, один worker, общие PostgreSQL и хранилище файлов. Код разделён по ответственности аналогично `frankenstein`, без отдельных микросервисов.

## Запуск

Из корня репозитория:

```bash
docker compose up -d db
docker compose --profile tools run --rm migrate alembic upgrade head
docker compose up -d --build api worker
curl -F 'file=@dataset/dataset2/болт1.pdf' http://localhost:8000/api/v1/jobs
```

Ответ содержит `id`. Затем запросить `/api/v1/jobs/{id}`. Когда `state` станет `succeeded` или `needs_review`, отчёт доступен по `/api/v1/jobs/{id}/artifacts/report.json`. DXF, если его удалось построить, доступен по `/api/v1/jobs/{id}/artifacts/result.dxf`. `needs_review` означает, что конвертер обнаружил объекты, которые нужно проверить вручную; при неизвестном масштабе DXF может отсутствовать. `failed` означает ошибку обработки; подробности есть в `error_code`, `error_message` и, если удалось записать, в `report.json`.

Первый запуск worker может скачать модель OCR в Docker volume `models`. Загрузка больше не является шагом сборки образа. Для отдельной диагностики загрузки есть `scripts/download_ocr_model.py` с ограничением времени.

Локальные тесты:

```bash
cd backend
uv sync --locked
uv run --frozen pytest -q
```

## Границы слоёв

| Слой | Ответственность |
| --- | --- |
| `api/v1`, `schemas`, `dependencies` | HTTP, валидация запроса, внедрение зависимостей и перевод ошибок в HTTP |
| `use_cases` | Создание задания, повторный запуск, чтение статуса и артефакта |
| `domain` | Формат `DrawingGraph` и инварианты геометрии |
| `services` | Подготовка изображения, сборка распознанного графа, экспорт DXF и preview |
| `repositories`, `uow` | Запросы к данным и граница транзакции |
| `infra` | SQLAlchemy, файловое хранилище, подключение CV-прототипа |
| `tasks`, `worker` | Очередь в PostgreSQL и обработка заданий вне HTTP-процесса |

Это слоистый монолит с use case и UoW, а не строгое DDD: use case и сервисы ещё знают конкретные SQLAlchemy/файловые реализации. Абстрактные порты здесь пока не дают пользы, потому что адаптеров БД и хранилища по одному. CPU-операции OCR/OpenCV/PDF/DXF работают только в worker и вызываются через `asyncio.to_thread`; HTTP и запросы к БД асинхронные. Очередь на PostgreSQL использует блокировки строк. Для текущей нагрузки отдельный Redis/RQ/Dramatiq не требуется.

## Почему эти библиотеки

| Библиотека | Причина |
| --- | --- |
| FastAPI, Pydantic Settings | HTTP-контракт и конфигурация через переменные окружения |
| SQLAlchemy asyncio, psycopg, Alembic | Асинхронный доступ к PostgreSQL и миграции |
| PyMuPDF | Рендер одностраничного PDF для OCR/CV; backend использует именно его |
| Pillow | Декодирование и нормализация PNG/JPEG |
| OpenCV, scikit-image, SciPy, RapidOCR, ONNX Runtime | Зависимости встроенного CV/OCR-прототипа из `runs/klapan_png2dxf/pipeline_b` |
| ezdxf | Запись редактируемых DXF-примитивов и размеров |

`pypdfium2` встречается в исходном прототипе/инструкциях по экспериментам, но не нужен backend: здесь для PDF выбран PyMuPDF. Замена PDF-библиотеки не меняет сервисный API `ImageService.prepare`.

## Поля БД

| Таблица | Оставленные поля и зачем они нужны |
| --- | --- |
| `jobs` | `id` — внешний идентификатор; `filename` — имя исходника; `source_sha256` — проверка ручной правки; `source_ext` — поиск исходного файла; `state` — быстрый статус; `channel`, `conversation_id`, `event_id` — источник и идемпотентность входящих событий; `created_at` — время создания |
| `runs` | `id`, `job_id`, `number` — история повторных запусков; `state`, `stage` — выбор задания worker и прогресс; `parameters` — признак ручного графа; `error_code`, `error_message` — диагностика; `created_at`, `started_at`, `finished_at` — порядок и длительность обработки |
| `artifacts` | `id`, `run_id`, `name`, `relative_path` — привязка результатов к запуску и поиск файла |

Идентификаторы и временные метки по умолчанию создаёт PostgreSQL. В миграции убраны дублирующие/неиспользуемые `source_size`, `runs.schema_version`, `artifacts.size` и `artifacts.sha256`. Если происхождение через `channel` и `event_id` больше не требуется интеграциям, это отдельное упрощение контракта API и схемы БД.

## Контракт результата и границы задачи

Экспорт выполняет `DxfExporter.export(graph, path)`. Новые результаты хранятся в
`jobs/<job_id>/runs/<run_id>/`; старые каталоги с номером запуска читаются для совместимости.
Каждый элемент `runs` в ответе статуса содержит `artifacts` — имена реально зарегистрированных файлов.
При неизвестном масштабе сохраняются граф и отчёт со статусом `needs_review`, DXF не создаётся;
исправленный граф можно отправить через `POST /api/v1/jobs/{id}/drawing`.

Принадлежность заданий боту задаётся `channel` и `conversation_id`. Повторная доставка одного
`event_id` в этом канале возвращает существующее задание; другое значение диалога даёт 409.
Авторизация не входит в текущую задачу. TIFF, дополнительные режимы обработки, контрольные
точки и восстановление с конкретного этапа из общего архитектурного плана не входят в
перечисленный обязательный минимум backend-разработчика.
