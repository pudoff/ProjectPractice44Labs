## First PaddleOCR pass

Raw and normalized observations are in `../results/qa_samples/*.ocr.json`. The review worksheet is `qa_review.csv`; it includes the source image, text ID, original reading, normalized reading, notation, confidence, bounding box in source pixels, and empty `ground_truth` / `qa_note` columns for human review.

- PaddleOCR: 3.7.0; PaddlePaddle: 3.2.0; CPU.
- Detector: PP-OCRv5_mobile_det. Archive SHA-256: `50446E5D01AC2A73D5319C89513281F6578414C888C602F9AF13F93FEEFFFC58`.
- Recognizer: eslav_PP-OCRv5_mobile_rec. Archive SHA-256: `B9F70DA0CA2BBC4D4CB7BA406A2D023061178437D6A930F07C8CA18C6C591839`.
- The same page pixels were read at 0° and 90°, as configured by `mlocr/src/cli.py`. No PDF text layer was involved because these inputs are PNG.
- PaddleOCR resized some passes to its 4000 px side limit. That is logged by PaddleOCR; the source PNGs were not modified.

The first pass exposed a repeated mixed-alphabet misspelling of `Масштаб`: `Macwmad` was not corrected because the lookalike table did not include Latin `d` for Cyrillic `б`. After QA confirmed this word in the flange sheet, the vocabulary fold was extended narrowly; it changes `Macwmad` to `Масштаб` only when the result uniquely matches a known drawing word. Negative controls `M12`, `10m`, `item`, and the unspaced merged token `MaccaMacwmad` remain unchanged.

QA also confirmed that a dimension arrow at the left of `32` was read as `$` and an arrow at the right as `f` (`$32f`). `$` now becomes `Ø` only when the complete following token matches a plausible size/fit/tolerance pattern. `$32f` remains unchanged and gets `ambiguous_diameter_glyph` / `needs_review`; real checked cases such as `$140`, `$112`, and `$1002` retain the diameter glyph. `normalized_text` is the original baseline. `normalized_after`, `corrections_after`, and `review_after` are the current text plus pixel-based diameter recovery, regenerated by `python -m mlocr.evaluation.refresh_qa_normalization`.

On the 23 Ø-related candidates with a usable reviewed label, the updated run has 19 correct Ø placements (16 exact strings), one missed/reversed Ø, three number/tolerance errors, and no explicit false Ø additions. The false `$32f` candidate is preserved as ambiguous for review. Remaining reading errors include `Ø100+2` becoming `Ø1002` and `05φ` versus `Ø50`. The selected sheets contain word examples with genuine Cyrillic `м`, but no standalone `10m` or `м` unit; those controls currently have only direct normalization checks, not image QA.

## Other findings from the same review

These are separate from glyph/notation scoring and can overlap within one OCR region:

- 9 notes concern missing or misleading spaces, including labels/numbers separated by large gaps.
- 13 notes concern neighboring cells or extra text merged into one region.
- 17 notes concern description text returned as fragments; most fragments are individually readable, while a few have recognition errors too.
- 3 notes concern orientation. The reviewed set includes an upside-down 180° case; the user reports that wrong 90° readings are rare. The current OCR runner checks 0° and one 90° rotation, but not 180°.

Keep these as separate review categories. Spacing and merged cells are detection/layout issues; description fragments concern region grouping; rotation belongs to OCR pass selection. A character-normalization change should not be used to hide these errors.
