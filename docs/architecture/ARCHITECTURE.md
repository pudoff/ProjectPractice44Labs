# Итоговая архитектура: сервис «скан/PDF чертежа ЕСКД → редактируемый DXF»

Проект — совместная работа с 44labs. Документ — предложение команде после ревью
([REVIEW.md](REVIEW.md)) и экспериментов ([experiments/RESULTS.md](experiments/RESULTS.md)).
Стек: **FastAPI + OpenCV + OCR (ONNX) + ML (обучаемые детекторы/сегментация), ezdxf**.

## 1. Принципы (что делает архитектуру надёжной)

1. **Описание чертежа `DrawingGraph` — центральный контракт.** Распознаватели только добавляют в него наблюдения,
   экспортёр только читает принятую версию. Согласны с предложением `service-architecture.md`; ниже — конкретная схема.
2. **Все допуски — в миллиметрах листа и в долях измеренной толщины штриха, не в пикселях.** Эксперименты показали:
   константы, подобранные на рендере 600 dpi, на скане 200 dpi стирали 86 % чернил (см. RESULTS §3).
3. **Регистрация листа — отдельный этап по шаблону ГОСТ 2.301/2.104** (рамка, штамп 185×55, доп. графы, формат, масштаб).
   Эвристика «крайние длинные линии = край листа» сломала 5 из 9 реальных листов.
4. **Геометрия подчиняется размерам через решатель ограничений**, пиксели — наблюдения с весом. Конфликт
   «надпись ≠ геометрия» — это запись в `issues`, а не подмена текста размера.
5. **Детерминированное ядро + заменяемые распознаватели.** Правила работают сразу, ML-модели подключаются там,
   где правила измеримо проигрывают (стрелки и шум на сканах, OCR курсива ЕСКД, классы линий).
6. **Каждое изменение проверяется регрессионным набором** (`tools/compare_dxf.py` + наложение на растр) —
   тот же набор, на котором найдены 4 бага этого ревью.
7. **Офлайн.** Все веса в образе, ONNX Runtime (CPU/GPU), без облачных вызовов в рабочем контуре.
   VLM — необязательный модуль, включается только по метрикам.

### 2.1. Этапы и их контракты

| этап | вход → выход | реализация MVP (есть / проверено) | улучшение (ML / доработка) |
|---|---|---|---|
| маршрутизатор | файл → страницы, тип (vector/raster/mixed) | pypdfium2: наличие путей и текстовых объектов | — |
| векторный PDF | страница → примитивы, тексты с координатами | pypdfium2 page objects | важнее, чем кажется: `dataset2/3` — 124 PDF |
| предобработка | изображение → бинарное, `stroke_thin_mm`, `stroke_thick_mm`, перекос | Otsu, Hough-перекос (есть) | Sauvola, удаление пятен по размеру/форме, перспектива по рамке |
| **регистрация листа** | бинарное → `Sheet{format, px_per_mm_xy, origin, frame, title_block, view_scale}` | обрез/рамка 20/5 с выбором по согласию масштабов (исправлено в ревью) | поиск прямоугольника рамки + штампа 185×55 по шаблону; масштаб из штампа «1:2» |
| OCR | изображение + Sheet → `TextItem{text, alts, score, poly_mm, angle}` | RapidOCR ONNX, PP-OCRv5 eslav, 2 прохода (есть) | плитки в родном разрешении; дообучение распознавателя на шрифте ЕСКД + искажениях |
| символы | → `Arrow`, `Datum`, `Roughness`, `Dot` | морфология с порогом от тонкого штриха (исправлено) | детектор (RT-DETR/YOLOX, Apache-2.0) на сканах |
| векторизация | бинарное − текст − символы → `Line/Arc/Circle/Spline` с толщиной | скелет + рекурсивное деление 0,08 мм (есть, обобщается: F1@0,25 0,88–0,98) | толщина на примитив → MAIN/THIN; сшивание через пересечения |
| классификация ролей | примитивы → `role` | длина/участие в размерах (слабо: 0,09–0,76) | толщина + контекст + сегментация (этап 2) |
| топология | роли → грани, контуры, отверстия | — (нет) | shapely `polygonize` по MAIN-рёбрам, замыкание зазоров < 0,3 мм |
| штриховки | 45°-семейства → HATCH по граням | семейства с локальным шагом и круговой фазой (исправлено) | граница = грань топологии вместо заливки |
| аннотации | стрелки+линии+тексты → `Dimension` и др. | пары стрелок, выносные, текст по совпадению с измерением, R/угол/выноски (есть, ~74 % по значению) | половинные ⌀, цепочки, «2 отв.», буквенные (L), допуски; вид → масштаб |
| штамп | тексты → поля | ячейки формы 1 относительно рамки (есть) | ФИО рукописные — отдельная модель позже |
| решатель | граф + размеры → координаты | МНК по кластерам x/y (есть, частично) | `scipy.optimize.least_squares`: расстояния, ⌀/R, параллельность, касания, симметрия; анализ ранга |
| экспорт | принятый граф → DXF | `tools/eskd_dxf.py` (проверен LibreCAD + ODA) | профили слоёв/масштаба |
| контроль | DXF + исходник → метрики, issues | `verify`, наложение, `compare_dxf` | самопроверка: значение размера = измерение, замкнутость, «висячие» концы |

### 2.2. `DrawingGraph` (Pydantic, `drawing.json`, версия схемы в поле `schema`)

```text
DrawingGraph
├─ document: id, source_sha256, pages[], pipeline_version, models{name: version}
├─ sheet: format (A0…A4), orientation, px_per_mm_xy, origin_px, skew_deg, frame_mm, title_block_mm,
│         scale (из штампа), calibrated_on, confidence
├─ views[]: id, bbox_mm, label ("А(5:1)", "В", "вариант"), scale, rotation_mark
├─ primitives[]: id, kind (line|arc|circle|spline), geometry (мм листа), width_mm, role
│         (contour|thin|axis|hidden|dimension|extension|leader|hatch|frame|symbol|unknown),
│         view_id, confidence, source {stage, px_bbox}
├─ topology: faces[] {id, outer[edge ids], holes[], area_mm2}, gaps[], self_intersections[]
├─ hatches[]: id, face_ids, pattern, angle, spacing_mm, phase_mm
├─ texts[]: id, text_raw, alternatives[], score, poly_mm, angle, height_mm, role (note|title|label|dim)
├─ dimensions[]: id, type (linear|aligned|diameter|radius|angular), defpoints, measured_mm,
│         nominal (из надписи), text_raw, display ("%%c<>", "<>x45%%d"…), tolerance, view_scale,
│         arrows[], extension_ids[], text_id, refs (измеряемые примитивы), link_status
├─ annotations[]: roughness, datum, gdt_frame, leader, view_label — с ссылками на примитивы/тексты
├─ constraints[]: kind, refs, value, source (dimension_id|rule), status (applied|conflict|skipped), residual_mm
├─ title_block: {name, designation, material, mass, scale, sheet, developer, checker, …} + source text ids
├─ issues[]: code, severity, message, refs, region_mm
└─ export_profile: layers map, scale mode, font, dimstyle
```
Правила: идентификаторы стабильны между этапами; `display` размера по умолчанию содержит `<>` —
фиксированное число допустимо только с записью в `issues` (это одна из находок ревью для вариантов A и B).

### 2.3. Профили экспорта

| профиль | координаты | масштаб | слои | когда |
|---|---|---|---|---|
| `eskd_tz` (по умолчанию) | мм листа, лист 1:1 в Model | `DIMLFAC = 1/масштаб` в стиле — так сделаны 30 из 36 архивных DXF с масштабом ≠ 1:1 (стили `к1_2`=2, `к1_5`=5); выносные виды — свой `DIMLFAC` | MAIN/THIN/AXIS/DIMS/TEXT (+ скрытые = THIN+DASHED) — требование ТЗ | всегда |
| `natural` (опция) | натуральные мм детали в Model, лист в Layout/Viewport | масштаб вьюпорта | те же | если заказчик подтвердит |

Расширение набора слоёв (например, `PART_MAIN`, `SECTION_HATCH`) — только как дополнительный профиль:
ТЗ фиксирует пять слоёв.

## 3. Сервис

```mermaid
flowchart LR
    UI[Веб-интерфейс\nзагрузка, предпросмотр,\nissues, скачивание] --> API
    API[FastAPI api] -->|job| DB[(SQLite WAL\n→ PostgreSQL)]
    API --> FS[(Том jobs/\nоригиналы, артефакты)]
    W[worker CPU/GPU\nтот же образ кода] -->|claim job| DB
    W --> FS
    W --> M[(Том models/\nONNX-веса)]
    W -. опц. .-> VLM[vlm\nQwen3-VL-4B]
```

**API (FastAPI)**

| метод | путь | назначение |
|---|---|---|
| POST | `/api/v1/jobs` | загрузка файла (PDF/PNG/JPEG/TIFF) + параметры (`sheet`, `profile`, `mode=fast|accurate`) → `job_id` |
| GET | `/api/v1/jobs/{id}` | статус `queued/running/succeeded/needs_review/failed`, этап, проценты, тайминги |
| GET | `/api/v1/jobs/{id}/artifacts/{name}` | `result.dxf`, `result.dwg`, `preview.png`, `overlay.png`, `drawing.json`, `report.json` |
| POST | `/api/v1/jobs/{id}/rerun` | повтор с другими параметрами → новый `run_id` |
| PUT | `/api/v1/jobs/{id}/drawing` | (этап 2) исправленный `drawing.json` из редактора → пересборка DXF без распознавания |
| GET | `/health`, `/version` | состояние, версии моделей/кода |

**Worker** — отдельный процесс того же образа: забирает задание (`UPDATE … RETURNING`/`SKIP LOCKED`),
выполняет этапы, после каждого пишет контрольную точку (`stage.json`), поэтому повтор начинается с упавшего этапа.
Один worker = одна страница одновременно; масштабирование — числом worker-контейнеров.

**Хранилище**: `jobs/<job_id>/input/original.<ext>` (байты не меняются) и `jobs/<job_id>/runs/<run_id>/{drawing.json,
result.dxf, preview.png, report.json, stages/}`. В БД — задания, запуски, артефакты (пути, хеши, версии).

**БД**: SQLite (WAL) для демо на площадке заказчика — нет отдельного контейнера и настройки; тот же слой доступа
переключается на PostgreSQL при нескольких worker'ах. (Отличие от `service-architecture.md`, где PostgreSQL сразу.)

**Поставка (офлайн)**: `docker compose` из образов `api`, `worker-cpu` (или `worker-gpu` с onnxruntime-gpu, CUDA ≥ 12.8
для RTX 50xx), тома `jobs/`, `models/`. Python 3.12 в образах (колёса onnxruntime-gpu/torch для обучения; локальная
разработка на 3.14 подтверждена). Шрифт `isocpeur`/GOST — в образе для рендера предпросмотра.
Время листа CPU сейчас 8–28 с (цель заказчика ≤ 5–10 мин — запас на ML-модели есть).

## 4. Данные и ML

**Что есть на самом деле** (проверено): 127 реальных пар PNG(600 dpi)↔DXF, 72 + 52 пары PDF↔DXF (пересекаются по
деталям — нужен реестр и разбиение по детали), 2876 настоящих `DIMENSION` в реальных DXF; 150 синтетических пар —
без `DIMENSION`, с диагональными линиями во всех 150 эталонах и 36 нулевыми отрезками (для обучения непригодны без чистки).

**Разметка бесплатно из реальных пар.** Эталонный DXF совпадает с PNG после калибровки (F1@0,25 мм 0,88–0,98 у
текущего B — значит, системы координат сходятся). Рендер эталона по слоям даёт:
маски ролей пикселей, рамки стрелок/знаков, кропы текста со строкой, связи «размер → стрелки → текст → defpoints».
Поверх — аугментации «скан»: 150–300 dpi, поворот, размытие, шум, пятна, JPEG, обрезка по краю листа
(генератор уже есть: `experiments/robustness.py`).

| модель | задача | данные | лицензия/формат |
|---|---|---|---|
| сегментация (U-Net/SegFormer-lite, плитки 512²) | роли пикселей: контур/тонкая/ось/размер/текст/штриховка/фон | рендер реальных DXF + аугментации | Apache/MIT, ONNX |
| детектор символов (RT-DETR или YOLOX) | стрелки, шероховатость, базы, рамки допусков, точки | то же | Apache-2.0 (Ultralytics — AGPL, только по решению) |
| распознаватель OCR | дообучение PP-OCRv5 eslav на шрифтах ЕСКД, ⌀ ± ° × | синтетические строки + кропы из DXF | Apache-2.0, ONNX через RapidOCR |
| рукописные ФИО | доп. задача ТЗ | нужны реальные примеры | позже |
| VLM (Qwen3-VL-4B) | трудные фрагменты, выбор кандидата | без обучения, затем LoRA | только если даст выигрыш на регрессии |

Разбиение: по детали (имя/обозначение), а не по файлу; `клапан` и 10 приёмочных листов заказчика — вне обучения.

## 5. Оценка качества

| уровень | набор | инструмент | сейчас (B, после исправлений) |
|---|---|---|---|
| геометрия | 9 реальных листов (dev) | `tools/compare_dxf.py --align geom` F1@0,25/0,5/1 | см. RESULTS §2 |
| размеры | те же | recall по значению (новое) и по написанию | ≈0,7 по значению |
| текст | те же | CER по центру строки (новое) | 0,27–0,66 |
| скан | клапан → 200 dpi + искажения | то же | см. RESULTS §3 |
| редактируемость | LibreCAD + ODA DXF→DWG→DXF; GUI-протокол в AutoCAD/nanoCAD у заказчика | `docker/cad-validate`, `docker/oda-convert` | без потерь |
| приёмка | 10 листов заказчика, 1–5 по редактируемости/полноте/чистоте | эксперты | не трогаем до приёмки |

Сопоставление с оценкой экспертов: редактируемость ≈ доля настоящих DIMENSION с `<>` + число фрагментов на контур +
замкнутость граней; полнота ≈ recall геометрии/размеров/текста; чистота ≈ precision + число «висячих» коротких отрезков.

## 7. Риски

- **DWG**: ODA File Converter бесплатен, но не open source; включение в поставку заказчику требует проверки лицензии.
  Альтернатива — LibreDWG (GPL, запись DWG экспериментальная) или выдача только DXF (ТЗ: DWG — доп. задача).
- **Ассоциативность** DIMENSION в чужих CAD не гарантирована ни одним профилем; проверять GUI-протоколом у заказчика.
- **Синтетика** в текущем виде вредна для обучения (артефакты в эталонах).
- **Масштаб не 1:1** у 36 из 126 архивных листов — без чтения масштаба из штампа размеры будут неверны
  (сейчас B спасает только отношение «измерено/надпись» = стандартный масштаб, без подгонки геометрии).
- **Многолистовые эталоны**: 11 архивных DXF содержат несколько листов в одном Model Space — для обучения и оценки
  нужно вырезать лист, соответствующий PNG.
- **Сканы** реальных архивов (пятна, сгибы, карандаш) хуже нашей симуляции — нужны реальные примеры до спринта 3.
