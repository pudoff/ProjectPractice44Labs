# Ревью архитектуры: что сделано, что показали измерения, что оставить, убрать, изменить

Проект — совместная работа с 44labs. Ревьюируются: (1) прогон «клапан PNG → DXF» — вариант A (ручная
параметрическая перерисовка) и вариант B (автоматический конвейер `pipeline_b`); (2) предложение
`архитектура_кодекс/service-architecture.md` (далее — «предложение»). Итоговая архитектура — [ARCHITECTURE.md](ARCHITECTURE.md),
цифры — [experiments/RESULTS.md](experiments/RESULTS.md).

## 0. Коротко

- **Направление предложения верное, и его стоит взять за основу**: описание чертежа `DrawingGraph` как контракт,
  базовая линия CV + OCR + правила раньше любых VLM, VLM — только по метрикам, конечный автомат вместо «агента»,
  `needs_review` и список проблем, отдельные `api`/`worker`.
- **Главные пробелы предложения — не в схеме, а в фактах и в «скучных» этапах.** Данных в 25 раз больше, чем в нём
  указано (127 + 124 реальных пары, а не 5). Нет отдельного этапа регистрации листа, хотя именно он сломал 5 из 9 листов.
  Нет правила «никаких пиксельных констант» — его нарушение стёрло 86 % чернил на скане. Нет регрессионного набора с
  числами. Решение о масштабе и слоях отложено, хотя данные архива и ТЗ его уже определяют.
- **Наш вариант B обобщается по геометрии, но не по смыслу.** После семи исправлений, найденных этим ревью, на 9 новых
  листах F1 при 0,25 мм = 0,89–0,98. Размеры по значению ≈ 0,70, слои ≈ 0,5, на скане 200 dpi размеры ≈ 0,2. Значит,
  ML нужен для интерпретации (стрелки и символы на сканах, OCR, роли линий), а не для геометрии.
- **Убрать из MVP**: VK-бот, прямой «VLM рисует весь лист» (вариант C), 13-слойный профиль по умолчанию,
  обязательный PostgreSQL на демо-площадке.

## 1. Что было сделано и что из этого следует

| | вариант A — ручная перерисовка | вариант B — конвейер |
|---|---|---|
| как | инженер за ~1 ч пишет `build_variant_a.py`: геометрия от размерных чисел, касания, симметрия; растр — для привязки | без ручного ввода: калибровка → OCR → стрелки → векторизация → штриховка → размеры → подгонка → DXF |
| клапан vs эталон, F1@0,25 | **0,980** | 0,921 (0,931 после ревью) |
| размеры | 28/28 настоящих DIMENSION, по значению 1,00 | по значению 0,93 (0,86 после ревью, см. RESULTS) |
| новые листы | не применимо (каждый лист — новый скрипт) | 9 листов: до ревью 4 работали, 5 ломались; после ревью F1@0,25 0,89–0,98 |
| скан 200 dpi | — | геометрия 0,40 → 0,79 после ревью; размеры ≈ 0,2; обрезанный по краю скан не калибруется |
| время | ~1 ч на лист | 8–28 с на лист (CPU) |

Выводы для архитектуры:
1. **A — это ручное составление `DrawingGraph` + решатель в голове инженера.** Такая работа не масштабируется, но в продукте
   нужна дважды: как редактор спорных мест (`needs_review`) и как способ создавать эталоны.
2. **Метрики B в первом отчёте были получены на единственном листе, на котором его отлаживали.** Проверка на 9 листах
   сразу выявила пять провалов калибровки. Регрессионный набор — обязательная часть архитектуры, а не опция.
3. **Ошибки B оказались инженерными, а не «нехваткой интеллекта»**: границы штриха, циклическая статистика, глобальная
   статистика вместо локальной, маска, которая расширяется целиком, пороги в пикселях. VLM их не исправит; их
   исправляют контракты этапов и тесты.

## 2. Ревью кода и практик (наш прогон)

### 2.1. Оставить (проверено измерениями)

| что | почему |
|---|---|
| `tools/eskd_dxf.py`: R2007, UTF-8 + `doc.encoding="cp1251"`, слои ТЗ, стиль ESKD, `$DIM*` в заголовке | LibreCAD открывает; ODA DXF→DWG→DXF без потерь для A и B |
| настоящие DIMENSION с `%%c<>`, `<>x45%%d`, `DIMLFAC` для видов в масштабе | этого требует заказчик, и так устроено 30 из 36 архивных листов с масштабом ≠ 1:1 |
| калибровка px → мм листа (теперь с гипотезой «рамка») | после исправления все 9 листов совпадают с эталоном до 0,1–0,3 мм |
| векторизация скелет → рекурсивное деление (допуск 0,08 мм) | F1@0,25 0,89–0,98 на новых листах; дуги аналитические |
| RapidOCR (ONNX, PP-OCRv5 eslav), два прохода 0°/90°, целевой OCR окна | офлайн, CPU, 2–4 с; кириллица ЕСКД читается на чистых листах |
| сборка размеров: пара встречных стрелок + выносные + текст, **значение которого совпадает с измерением** | «самопроверка» без эталона; ≈0,7 по значению на новых листах; отношение = стандартный масштаб → `DIMLFAC` |
| семейства параллельных штрихов → HATCH с измеренными шагом и фазой | работает на 8 из 9 листов (60–85 % площади) |
| поля штампа по геометрии формы 1 ГОСТ 2.104 + пользовательские свойства DXF | простое и проверяемое решение для поиска по архиву |
| валидация: `verify` + LibreCAD (Docker) + ODA-круг + наложение на исходник + `compare_dxf` | каждая проверка ловила свой класс ошибок |

### 2.2. Изменить

| что сейчас | проблема (факт) | как надо |
|---|---|---|
| `run()` на 500 строк, словари, правка списков «на месте» | нельзя измерить вклад этапа, нельзя повторить с этапа, нельзя исправить вручную | этапы с контрактами поверх `DrawingGraph` (Pydantic), контрольные точки после каждого |
| калибровка «крайние длинные линии» | 5/9 листов без линии обреза; на обрезанном скане крайние — доп. графы | регистрация по шаблону ГОСТ: рамка + штамп 185×55 + доп. графы, проверка согласия масштабов x/y |
| пиксельные/мм-константы с рендера 600 dpi | стирание 86 % чернил на скане; «адаптация по медиане» сломала 3 чистых листа | размеры через толщину тонкой линии (20-й процентиль) и мм; регрессия до/после |
| глобальная статистика (шаг штриховки по всему листу) | решение 14:13 переворачивалось от сдвига на 0,06 мм | локальные оценки по региону/виду; круговые величины — круговой статистикой |
| слой по длине отрезка (≥ 1,5 мм → MAIN) | классы слоёв 0,09–0,73 | толщина каждого примитива + контекст (размер/выноска/штриховка) + сегментация (этап 2) |
| текст размера — число, если совпало с измерением (`fmt(v)`); в A — фиксированные `R7`, `R2`, `60°`, `M12x1,5-H7` | фиксированное число не следует за геометрией; `R2` над канавкой r 1,5 в A — замаскированный конфликт | всегда `<>` с префиксом/суффиксом; фиксированное число — только с записью в `issues` |
| подгонка под размеры — МНК по кластерам x/y | только горизонтальные/вертикальные размеры, без R/⌀/углов/касаний | решатель `least_squares` по ограничениям графа, проверка ранга/невязок, конфликты → `issues` |
| граница штриховки заливкой по растру | «протекает», площадь 60–85 % | грани планарного графа контуров (shapely `polygonize`) |
| масштаб листа не читается из штампа | 36/126 архивных листов не 1:1 | масштаб из штампа → `DIMLFAC` в стиле; масштабы видов из меток «А(5:1)» |
| метрика: `--align bbox`, точная строка размера | ложные провалы: DEFPOINTS, `∅`/`Ø`, кириллица | исправлено (`--align geom`, нормализация, recall по значению); для сканов — регистрация RANSAC/ICP |

### 2.3. Убрать / не переносить в продукт

- Скрипты под конкретный лист (`build_variant_a.py`, `work/*`) — это эталон и материал для тестов, а не код продукта.
- `matplotlib` как основной рендер предпросмотра: медленно, требует обходных приёмов. Для сервиса нужен рендер ezdxf
  в SVG/PNG без фигур matplotlib (или PyMuPDF/cairo), а наложение — в веб-интерфейсе.
- Зависимость кода от каталога инструментов разработки: общие модули перенесены в `tools/` и `docker/`.
- Синтетический набор `dataset/data` в нынешнем виде — из обучения и метрик (эталоны с артефактами, без DIMENSION).

## 3. Ревью предложения `service-architecture.md`

### 3.1. Согласен — оставить как есть

- Гибрид «базовая линия CV + OCR + правила → затем точечные модели → VLM только по метрикам»; отказ от универсального
  конвертера с нуля.
- `DrawingGraph` (`drawing.json`) с разделами `primitives / topology / texts / dimensions / constraints / issues /
  provenance / export_profile`; хранение номинала, измерения и надписи раздельно; стабильные идентификаторы.
- Конечный автомат на Python вместо «агента»; VLM получает фрагмент и кандидатов, отвечает по JSON-схеме, правоту
  решает валидатор, а не уверенность модели.
- Отдельная ветка для векторных PDF (в `dataset2/3` 124 PDF — это не редкость), маршрутизация по содержимому страницы.
- Различение пикселей скана, мм листа и мм детали; масштабы по видам.
- Принцип «конфликт не маскируется текстом размера» (наш вариант A его нарушал — см. 2.2).
- Различие «есть DIMENSION» и «ассоциативность в CAD»; GUI-протокол проверки у заказчика.
- `api` и `worker` — разные процессы, задания не держат HTTP; хранилище `jobs/<job_id>/runs/<run_id>/`; статусы
  `queued → running → succeeded / needs_review / failed`.
- Разбиение данных по детали; 10 приёмочных листов не трогать; публиковать пороги метрик до сравнения; результаты по
  каждому листу, а не только среднее.

### 3.2. Исправить факты

| в предложении | на самом деле (проверено) |
|---|---|
| «150 синтетических и 5 реальных пар» | 127 реальных PNG(600 dpi)↔DXF + 72 + 52 PDF↔DXF (пересекаются по деталям); 2876 настоящих DIMENSION в реальных эталонах |
| «автоматически получить разметку размерных связей нельзя» | для синтетики — да; для реальных эталонов связи «DIMENSION → defpoints → текст → стрелки» читаются напрямую, а эталон совпадает с PNG после калибровки (F1@0,25 до 0,98) → разметку сегментации, детекции и связей можно получить рендером |
| диагонали в синтетическом эталоне | подтверждено: длинные диагональные LINE во **всех** 150 эталонах, 36 нулевых отрезков |
| ссылки на `valve-v2-cad-check.md`, `team-and-project-plan.md`, `terms-and-data-storage.md`, `png-to-editable-dxf-algorithm.md`, `sprint-01-detailed-plan.md` | в репозитории этих файлов нет — их выводы (клапан v2, 13 слоёв) проверить нельзя |

### 3.3. Изменить решения

| пункт предложения | что предлагаю | почему |
|---|---|---|
| Слои: «MAIN/THIN/AXIS/DIMS/TEXT расширяется … `PART_MAIN/DIMENSIONS/SECTION_HATCH` (13 слоёв в v2)» | по умолчанию **ровно пять слоёв ТЗ**; расширенный набор — отдельный профиль по запросу | ТЗ задаёт слои явно; эталонная синтетика заказчика использует те же пять |
| Профиль масштаба «фиксируется в первом спринте» (натуральная геометрия + viewport или лист + коэффициент) | решить сразу: **лист в мм в Model + `DIMLFAC = 1/масштаб`** (профиль `eskd_tz`); натуральный — опция | так сделаны 30 из 36 архивных листов с масштабом ≠ 1:1; заказчик: «формат и масштаб как в оригинале» |
| Первая реализация геометрии: «OpenCV, контуры, преобразование Хафа» | скелет → отрезки/дуги с допуском в мм (уже работает), Hough/LSD — только вспомогательно | Hough даёт отрезки без дуг и без точных концов; скелетный векторизатор измерен: 0,89–0,98 |
| OCR: PaddleOCR | те же модели PP-OCRv5 eslav, но через **RapidOCR + ONNX Runtime** в рабочем образе; Paddle — только для дообучения | без фреймворка Paddle в поставке, проще офлайн и GPU/CPU |
| «Обзорное изображение … фрагменты исходного разрешения» | согласен и уточняю: OCR — плитками в родном разрешении с перекрытием; **все пороги — в мм и через толщину тонкой линии** | измерено: константы 600 dpi стирали 86 % чернил на 200 dpi |
| `db`: PostgreSQL с первого спринта | **SQLite (WAL)** за тем же интерфейсом репозитория; PostgreSQL — при нескольких worker | демо ставится на площадке заказчика без интернета: меньше контейнеров и настройки |
| Решатель на SciPy «полезен для подгонки» | сделать его центральным этапом: размеры — жёсткие ограничения, пиксели — наблюдения, анализ ранга/невязок | требование заказчика «точность размеров 100 %» выполняется только так |
| VLM-кандидаты 4B / 8B / 9B на GPU 16–24 ГБ | в план — только Qwen3-VL-4B (квантованная), включать по метрикам; 8B/9B — после | 8B в fp16 ≈ 17 ГБ весов не помещается в 16 ГБ с кодировщиком; наши ошибки не «понимательные» |

### 3.4. Убрать из MVP

- **VK-бот**: требует интернета, не входит в ТЗ, противоречит офлайн-поставке. Можно сделать позже как внешний адаптер к тому же API.
- **Вариант C** («VLM → описание всего листа»): по нашим данным узкие места — регистрация, символы на сканах, OCR и роли
  линий; полнолистовая генерация их не решает, а время/память съест. Оставить исследовательской заметкой.
- Распределение ролей команды и часы внутри архитектурного документа — перенести в план проекта.
- Qwen3.5-9B в списке кандидатов первого сравнения.

### 3.5. Добавить (в предложении нет)

1. **Регистрация листа** как отдельный этап: рамка по ГОСТ 2.301, штамп 185×55, доп. графы, формат, масштаб из штампа,
   проверка согласия масштабов.
2. **Правило независимости от разрешения** (мм + толщина тонкой линии) и **локальность статистик**.
3. **Регрессионный набор с цифрами** и обязательный прогон до/после изменения (`docs/architecture/experiments/`):
   9 чистых реальных листов, клапан, скан-симуляция, синтетика.
4. **Генератор разметки из реальных пар** (рендер эталонов по ролям + скан-аугментации) — основа для детектора символов,
   сегментации ролей и дообучения OCR.
5. **Подводные камни оценки**: многолистовые эталоны (11 файлов), рамка на `DEFPOINTS`, разные знаки ⌀, кириллица/латиница —
   иначе метрики врут в обе стороны.
6. **Лицензии**: ODA File Converter (DWG) — не open source, решение о поставке; Ultralytics — AGPL, предпочесть Apache-2.0
   детекторы (RT-DETR, YOLOX).
7. **Образы на Python 3.12** (колёса onnxruntime-gpu, torch для обучения; CUDA ≥ 12.8 для RTX 50xx); шрифт ГОСТ/isocpeur
   в образе для предпросмотра.
8. **Редактор `drawing.json`** в веб-интерфейсе (этап 2): исправление спорных мест и пересборка DXF без повторного
   распознавания — это продуктовый вариант нашего варианта A.

## 4. Решение

Брать предложение за каркас, внести правки разделов 3.2–3.5 и реализовывать по [ARCHITECTURE.md](ARCHITECTURE.md).
Ядро распознавания — перенос `pipeline_b` (с исправлениями ревью) в пакет со стадиями поверх `DrawingGraph`; первый
спринт — регистрация листа, масштаб из штампа, API/worker, регрессия в CI.
